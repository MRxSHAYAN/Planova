1. OVERVIEW
================================================================================
Planova is a full-stack web platform for managing expos, trade shows, and
conferences across Pakistan. It connects three types of users:

  Admin      —  Creates and manages expos, approves/rejects exhibitor
                applications, assigns booths, manages sessions, broadcasts
                emails, views reports & analytics, manages contact messages.

  Exhibitor  —  Applies to expos, manages booth and products/services,
                updates company profile, requests booth changes.

  Attendee   —  Registers for expos, views sessions and exhibitors,
                saves sessions, manages profile.

All data lives in MongoDB — there are no hardcoded/static data files. Every
list, count, and stat is fetched from the database via REST API calls.

4. HOW TO RUN (step by step)
================================================================================
Prerequisites:
  - Node.js 20+ installed
  - MongoDB running locally (or a MongoDB Atlas URI)
  - Gmail account with 2FA enabled + App Password generated

OPTION A — Run both together from root (recommended)

  npm install                         ← install root devDependencies (concurrently)
  npm run install:all                 ← install client + server dependencies
  npm run dev                         ← starts both client (port 5173) + server (5000)

OPTION B — Run separately

  # Terminal 1: Server (port 5000)
  cd server
  npm install
  npm run dev                         ← uses nodemon for hot-reload

  # Terminal 2: Client (port 5173)
  cd client
  npm install
  npm run dev                         ← uses Vite dev server

PROXY:
  The Vite dev server proxies /api/* requests to http://localhost:5000
  (configured in client/vite.config.js). No CORS issues in development.

CORS:
  Server allows origin from CLIENT_URL env variable (default: http://localhost:5173).

PRODUCTION BUILD:
  cd client && npm run build          ← outputs to client/dist/

SEED THE DATABASE:
  cd server && npm run seed           ← wipes all data and populates demo data
  (or: node seed.js)

  SMTP_HOST=smtp.gmail.com                          ← email SMTP host
  SMTP_PORT=587                                     ← SMTP port (TLS)
  SMTP_USER=your_email@gmail.com                    ← Gmail address
  SMTP_PASS=<16_char_app_password>                  ← Gmail App Password

IMPORTANT NOTES:
  - For Gmail: enable 2-Factor Authentication, then generate an App Password
    at https://myaccount.google.com/apppasswords
  - No leading/trailing spaces in .env values — Nodemailer will fail silently
  - JWT tokens expire in 7 days (set in generateToken.js)

6. DATABASE CONNECTION (config/db.js)
================================================================================
File: server/config/db.js

  - Uses mongoose.connect() with the MONGO_URI from .env
  - Connection is cached globally (global.mongooseConn) to avoid multiple
    connections in serverless environments (Vercel)
  - Every incoming request runs through a middleware in index.js that calls
    connectDB() — this ensures lazy connection on first request
  - Throws an error if MONGO_URI is not set

How it works in index.js:
  app.use(async (_req, _res, next) => {
    await connectDB();
    next();
  });

This pattern ensures the DB is connected before any route handler runs,
and it's safe for serverless cold starts.

7. AUTH SYSTEM — JWT, MIDDLEWARE, OTP
================================================================================

▸ TOKEN GENERATION  (server/utils/generateToken.js)
  - Uses jsonwebtoken to sign a JWT with { userId, role }
  - Secret: process.env.JWT_SECRET
  - Expiry: 7 days
  - Called after login, OTP verification, email/password change confirmation

▸ AUTH MIDDLEWARE  (server/middleware/authMiddleware.js)
  Two exported functions:

  protect(req, res, next)
    - Reads Authorization header ("Bearer <token>")
    - Verifies token with jwt.verify()
    - Sets req.user = { userId, role }
    - Returns 401 if token is missing or invalid

  requireRole(role)
    - Returns middleware that checks req.user.role === role
    - Returns 403 "Forbidden: wrong role" if mismatch

  Usage in routes:
    router.get("/mine", protect, requireRole("attendee"), handler);
    router.post("/", protect, requireRole("admin"), handler);

▸ OTP SYSTEM  (server/routes/authRoutes.js + server/utils/sendEmail.js)
  - OTP is a 6-digit random number: Math.floor(100000 + Math.random() * 900000)
  - OTP expiry: 10 minutes (OTP_EXPIRY = 10 * 60 * 1000)
  - OTP is stored on the User document: otp, otpExpiry, otpPurpose
  - Purposes: "verify", "email-change", "password-change", "forgot-password"
  - Cleared after successful verification

▸ REGISTRATION FLOW
  1. POST /api/auth/register — creates unverified user, sends OTP email
     - If email send fails, the user is deleted (rollback)
     - Cannot register as "admin"
  2. User enters OTP on Register page
  3. POST /api/auth/verify-otp — marks isVerified=true, returns JWT + user

▸ LOGIN FLOW
  1. User picks role card (attendee or exhibitor) on Login page
  2. POST /api/auth/login with { email, password, role }
  3. Server finds user by { email, role }, checks:
     - Password match (bcrypt.compare)
     - isActive (not deactivated by admin)
     - isVerified (email verified)
  4. Returns user object + JWT
  5. Frontend stores token as "planova_token" in localStorage
  6. Frontend stores user as "planova_user" in localStorage

▸ FORGOT PASSWORD FLOW
  1. User picks role + enters email on ForgotPassword page
  2. POST /api/auth/forgot-password — finds { email, role }, sends OTP
  3. User enters OTP + new password
  4. POST /api/auth/reset-password — validates OTP, sets new password

▸ EMAIL CHANGE (logged in)
  1. POST /api/auth/request-email-change — sends OTP to the NEW email
  2. POST /api/auth/confirm-email-change — verifies OTP, updates email

▸ PASSWORD CHANGE (logged in)
  1. POST /api/auth/request-password-change — sends OTP to current email
  2. POST /api/auth/confirm-password-change — verifies OTP, updates password
  Note: pendingPassword is stored as plain text temporarily, then hashed
  via the pre("save") hook when user.password is set and save() is called.

8. EMAIL SYSTEM — NODEMAILER & SMTP
================================================================================
File: server/utils/sendEmail.js

▸ TRANSPORTER
  - Creates a Nodemailer transporter with SMTP config from .env
  - Host: SMTP_HOST (e.g. smtp.gmail.com)
  - Port: SMTP_PORT (587 for TLS)
  - secure: false, requireTLS: true
  - Auth: SMTP_USER + SMTP_PASS
  - New transporter created per function call (makeTransporter())

▸ EMAIL TEMPLATES
  All emails use a branded HTML template with:
  - Planova logo (embedded as CID attachment from client/src/assets/Icon.png)
  - Dark navy header (#09152E)
  - Clean body with styled content
  - Footer with branding

▸ EMAIL FUNCTIONS (5 total)

  1. sendOTPEmail(to, otp, purpose)
     Sends a 6-digit OTP code. Purposes:
       "verify"           → subject: "Planova - Verify your email"
       "email-change"     → subject: "Planova - Confirm your new email"
       "password-change"  → subject: "Planova - Confirm password change"
       "forgot-password"  → subject: "Planova - Reset your password"

  2. sendApplicationStatusEmail(to, companyName, expoTitle, status, rejectReason)
     Sent when admin approves or rejects an exhibitor application.
       approved → green banner: "Your application has been approved"
       rejected → red banner with reject reason

  3. buildBroadcastEmail(expoTitle, recipientName, subject, message)
     Builds HTML for admin broadcast emails. Returns { html, attachments }.
     Used by broadcastRoutes.js to send bulk emails.

  4. sendWelcomeEmail(to)
     Sent when someone subscribes to the newsletter.
     Subject: "Planova - Subscribed to expo alerts"

  5. generateOTP()
     Returns a random 6-digit string.

▸ IMPORTANT NOTES
  - Email failure on registration causes a rollback (user deleted)
  - Email failure on approve/reject is NON-CRITICAL (action still succeeds)
  - Email failure on newsletter subscribe is NON-CRITICAL (logged to console)
  - All emails sent from: "Planova" <SMTP_USER>

9. FILE UPLOAD — MULTER
================================================================================
File: server/routes/uploadRoutes.js

  - Uses multer for disk storage uploads
  - Files saved to: server/uploads/
  - Filename format: <timestamp>-<random>.<ext>
  - Max file size: 5 MB
  - Allowed types: .jpg, .jpeg, .png, .webp, .gif
  - Requires authentication (protect middleware)
  - Returns URL: /uploads/<filename>
  - The uploads directory is served as static files via express.static()
    in index.js: app.use("/uploads", express.static("uploads"))

  Endpoint:
    POST /api/upload — upload single image (field name: "file")
    Returns: { url: "/uploads/1698765432-123456.jpg" }

  Used by: avatar uploads, expo images, product images via the
  ImageUpload.jsx component on the frontend.

10. PASSWORD RULES
================================================================================
  - Minimum 7 characters
  - At least one number (0-9)
  - At least one special character (!@#$%^&* etc.)

Enforced in THREE places:
  1. server/routes/authRoutes.js       → validatePassword() function
     (register, request-password-change, reset-password endpoints)
  2. client Register.jsx               → pwCheck() function
  3. client ForgotPassword.jsx          → pwCheck() function

11. MULTI-ROLE ACCOUNTS
================================================================================
The same email address can register as BOTH an attendee AND an exhibitor.
They are stored as two separate User documents in MongoDB.

Schema design:
  - The email field is NOT globally unique
  - Unique compound index: { email: 1, role: 1 }
  - This means email + role together must be unique

Login, forgot-password, and reset-password all accept a "role" field
and query { email, role } to find the correct account.

To apply the index on an existing DB (one-time):
  mongosh planovaDB --eval "
    db.users.dropIndex('email_1');
    db.users.createIndex({ email: 1, role: 1 }, { unique: true });
  "

19. FRONTEND — AUTH CONTEXT & ROUTE PROTECTION
================================================================================

▸ AuthContext  (client/src/context/AuthContext.jsx)
  Provides { user, login, updateUser, logout } to the entire app.

  login(userData)
    → Stores token as "planova_token" in localStorage
    → Stores user object as "planova_user" in localStorage
    → Sets React state

  updateUser(updatedFields)
    → Merges new fields into existing user
    → Updates localStorage and React state

  logout()
    → Removes "planova_token" and "planova_user" from localStorage
    → Clears React state

  On app load:
    → Reads "planova_user" from localStorage to restore session

▸ PrivateRoute  (client/src/components/PrivateRoute.jsx)
  Two components:

  PrivateRoute({ children, role })
    → Checks user from AuthContext OR localStorage (fallback)
    → Redirects to /login if not authenticated or wrong role

  AdminRoute({ children })
    → Same logic but checks role === "admin"
    → Redirects to /admin/login

▸ useProfile Hook  (client/src/hooks/useProfile.js)
  → Fetches GET /api/auth/profile with JWT
  → Returns { profile, loading, error, refresh }
  → Also exports updateProfile(data) for PUT /api/auth/profile
  → Exports initials(name) helper: "Ali Hassan" → "AH"

22. KNOWN LIMITATIONS / NOT YET BUILT
================================================================================
These are known gaps. Not broken — just not built yet.

  ▸ Saved exhibitors
    Attendees can save sessions to DB (done). Saving exhibitors is not
    fully wired — the Bookmark model exists but the SavedItems page
    only shows saved sessions.

  ▸ Attendee Overview right column
    The attendee Overview page has a 5-col grid but only the left 3-col
    section renders. The right 2-col panel is empty. Could show: upcoming
    sessions for today, or a mini exhibitor spotlight.

  ▸ No public expo detail page (/expos/:id)
    The public Explore Expos page shows a modal for each expo but there
    is no dedicated shareable URL for a single expo page.

  ▸ No attendee notifications
    Attendees receive no in-app or email notification when an expo they
    registered for is updated, cancelled, or a new session is added.

  ▸ No pagination
    All list endpoints return all documents. For production with large
    datasets, pagination (?page=&limit=) should be added.
