1. WHAT IS PLANOVA
================================================================================
Planova is a full-stack web platform for managing expos, trade shows, and
conferences in Pakistan. It connects three types of users:

  - Attendees   -- browse expos, register, view sessions, explore exhibitors
  - Exhibitors  -- apply to expos, manage booths and products
  - Admins      -- manage everything: expos, booths, applications, users, reports

4. HOW TO RUN
================================================================================
Prerequisites: Node.js 20+, MongoDB running locally

  # Server (port 5000)
  cd server
  npm install
  npm run dev

  # Client (port 5173, proxies /api/* to port 5000)
  cd client
  npm install
  npm run dev

  # Production build
  cd client && npm run build
  # Serve dist/ with any static server or Express

6. DATABASE MODELS
================================================================================
User
  _id, name, email (not globally unique -- see section 18), password (hashed),
  role (attendee | exhibitor | admin), phone, city, company, category,
  description, website, avatar (URL string), isActive, isVerified,
  otp, otpExpiry, otpPurpose, pendingEmail, pendingPassword
  INDEX: { email: 1, role: 1 } UNIQUE  -- same email allowed per unique role

Expo
  _id, title, city, venue, dateStart, dateEnd, status (upcoming|published|archived),
  category, description, image (URL), totalBooths, createdAt

Session
  _id, event (-> Expo), title, speaker, speakerRole, type (Keynote|Panel|Workshop|Talk),
  date, time, duration, room, description

Registration
  _id, user (-> User), event (-> Expo), status (confirmed), registeredAt

Application
  _id, user (-> User), expo (-> Expo), companyName, boothRequested (-> Booth),
  status (pending|approved|rejected), createdAt
  NOTE: file may be named Application.js or applicationRoutes.js

Booth
  _id, expo (-> Expo), number, size, price, status (available|pending|occupied)

Product
  _id, exhibitor (-> User), name, description, price, image (URL), createdAt

Newsletter
  _id, email, createdAt

9. AUTH & OTP SYSTEM
================================================================================
Registration flow:
  1. POST /api/auth/register -- creates unverified user, generates 6-digit OTP,
     sends OTP email, returns { message: "OTP sent to email" }
  2. User enters OTP on Register page (6 boxes)
  3. POST /api/auth/verify-otp -- marks isVerified=true, returns user + JWT

Login flow:
  1. User picks role card (attendee or exhibitor)
  2. POST /api/auth/login with { email, password, role }
  3. Server finds user by { email, role }, checks password, checks isVerified
  4. Returns user object + JWT
  5. Client stores JWT in localStorage as "planova_token"
  6. Client redirects based on data.role field in response

Forgot password flow:
  1. User picks role card + enters email
  2. POST /api/auth/forgot-password with { email, role }
  3. Server finds { email, role }, generates OTP, sends email
  4. User enters OTP + new password
  5. POST /api/auth/reset-password with { email, role, otp, newPassword }

Email change (logged in):
  POST /api/auth/request-email-change   -- OTP sent to new email
  POST /api/auth/confirm-email-change   -- OTP verified, email updated

Password change (logged in):
  POST /api/auth/request-password-change  -- OTP sent to current email
  POST /api/auth/confirm-password-change  -- OTP verified, password updated

OTP expiry: 10 minutes

10. PASSWORD REQUIREMENTS
================================================================================
  - At least 7 characters
  - At least one number (0-9)
  - At least one special character (!@#$%^&* etc.)
  - NO letter requirement (removed)

Validated in:
  - server/routes/authRoutes.js  validatePassword()
  - client Register.jsx          pwCheck()
  - client ForgotPassword.jsx    pwCheck()

11. EMAIL SYSTEM
================================================================================
File: server/utils/sendEmail.js

Uses Nodemailer with generic SMTP (works with Gmail, Outlook, etc.)
Transporter is created once and reused.

Email types sent:
  - "verify"          OTP to verify new account
  - "email-change"    OTP to confirm new email address
  - "password-change" OTP to confirm password change
  - "forgot-password" OTP to reset forgotten password

Each email has a styled HTML template with the 6-digit code.

Gmail setup: enable 2FA + generate App Password, use it as SMTP_PASS.
IMPORTANT: No leading spaces in .env values.

14. EXPOS & SESSIONS
================================================================================
Expo statuses: upcoming, published, archived
  - Only non-archived expos appear on the public Explore page
  - Admin can archive via PUT /api/expos/:id/close

Sessions belong to an expo (event field).
Session types: Keynote, Panel, Workshop, Talk

Public /schedule page shows ALL sessions.
Attendee /my-schedule shows ONLY sessions for expos the attendee registered for.
  - Implemented via GET /api/sessions/mine (server-side filter)
  - Server looks up attendee's registrations, returns sessions WHERE event IN registeredExpoIds

15. EXHIBITOR APPLICATIONS & BOOTHS
================================================================================
Application flow:
  1. Exhibitor picks expo on Apply page
  2. Available booths for that expo loaded from GET /api/booths/expo/:expoId
  3. Exhibitor picks a booth, submits application
  4. Admin approves / rejects on Applications page
  5. On approval, booth status set to "occupied"

Booth change request:
  - Exhibitor can request booth change on My Applications
  - PUT /api/applications/:id/booth-change

Booth statuses: available, pending, occupied

17. MY SCHEDULE (ATTENDEE)
================================================================================
Approach:
  Client calls GET /api/sessions/mine (with JWT Bearer token).
  Server:
    1. Finds all Registration documents for req.user.userId
    2. Extracts expo IDs
    3. Returns Session.find({ event: { $in: expoIds } }) with event populated

This avoids any client-side ObjectId comparison bugs (previous approach used
.includes() which failed due to reference equality on ObjectId objects).

If the attendee has no registrations, returns empty array [].
Page shows empty state: "Register for an expo to see its sessions here."

18. USER ROLES & MULTI-ROLE ACCOUNTS
================================================================================
Users can register the SAME email as both attendee and exhibitor.
These are separate User documents in MongoDB.

Schema: email field is NOT globally unique.
Index:  { email: 1, role: 1 } UNIQUE
  -- same email can exist once as "attendee" and once as "exhibitor"
  -- same email cannot register as attendee twice

Login: POST /api/auth/login with { email, password, role }
  -- server queries { email, role } to find the correct account
  -- the role card on the login page determines which account to authenticate

Forgot password: POST /api/auth/forgot-password with { email, role }
  -- role picker shown on ForgotPassword page

Admin accounts: still use unique email (role=admin enforced separately).

MongoDB index migration:
  -- old:  { email: 1 } unique
  -- new:  { email: 1, role: 1 } unique
  -- drop via: db.users.dropIndex("email_1")
  -- applied in production via mongosh on server restart

  to compare MongoDB ObjectId values reliably in JavaScript.
