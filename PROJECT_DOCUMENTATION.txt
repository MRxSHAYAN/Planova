1. WHAT IS PLANOVA?
================================================================================

Planova is a web platform for managing expos (exhibitions) in Pakistan.
It has three types of users:

  - ATTENDEE   — browses expos, registers for sessions, views schedules
  - EXHIBITOR  — applies to expos, manages booths, builds a company profile
  - ADMIN      — manages the whole platform (users, expos, applications, booths)

The public website shows upcoming expos, schedules, and general information.
Each role has its own private dashboard after login.

4. HOW TO RUN THE PROJECT
================================================================================

REQUIREMENTS
  - Node.js v18 or higher
  - MongoDB running locally OR a MongoDB Atlas connection string

STEP 1 — Install all dependencies

  From the root folder run:
    npm install

  This installs root + client + server dependencies together (if configured).
  If not, run separately:
    cd server && npm install
    cd client && npm install

STEP 2 — Set up environment variables

  Copy or edit server/.env (see Section 5 below).
  At minimum you need MONGO_URI and JWT_SECRET.

STEP 3 — Seed the database (creates demo users)

  cd server
  node seed.js

  This creates:
    admin@planova.com        / admin123      (admin)
    raza.ahmed@techbridge.pk / exhibitor123  (exhibitor)
    ayesha.siddiqui@email.com / attendee123  (attendee)

STEP 4 — Start both servers

  From the root folder:
    npm run dev

  OR start them separately:
    cd server && npm run dev     ← runs on http://localhost:5000
    cd client && npm run dev     ← runs on http://localhost:5173

  The Vite dev server proxies /api/* to http://localhost:5000 automatically
  (configured in client/vite.config.js). This means the frontend just calls
  fetch("/api/auth/login") and it reaches the backend without any CORS issues.

STEP 5 — Open the app

  http://localhost:5173

6. DATABASE & MODELS
================================================================================

All data lives in MongoDB. The main model used so far is User.

USER MODEL (server/models/User.js)
  name          String   — full name
  email         String   — unique, lowercase
  password      String   — hashed with bcrypt (never stored plain)
  role          String   — "attendee" | "exhibitor" | "admin"
  phone         String   — optional
  city          String   — optional
  company       String   — company name (mainly for exhibitors)
  category      String   — industry/category (exhibitors)
  description   String   — about the company (exhibitors)
  website       String   — company website (exhibitors)
  avatar        String   — profile picture URL (future use)
  isActive      Boolean  — false = account deactivated by admin
  isVerified    Boolean  — false until email OTP is confirmed
  otp           String   — temporary 6-digit OTP code
  otpExpiry     Date     — OTP expires 10 minutes after creation
  pendingEmail  String   — stores new email while waiting for OTP (email change)
  createdAt     Date     — auto from Mongoose timestamps
  updatedAt     Date     — auto from Mongoose timestamps

OTHER MODELS (schema defined but not yet wired to live API routes)
  Event.js         — expo events
  Session.js       — talks/sessions within an event
  Exhibitor.js     — exhibitor application to an event
  Registration.js  — attendee registration for an event
  Booth.js         — booth assignment
  Bookmark.js      — saved items (events, sessions)

PASSWORD HASHING
  Passwords are hashed automatically in a Mongoose pre-save hook using bcrypt
  with a salt round of 10. Plain passwords are NEVER saved to the database.

7. BACKEND API ROUTES
================================================================================

Base URL in development: http://localhost:5000
All routes are under: /api/auth/

─── REGISTRATION ────────────────────────────────────────────────────────────

POST /api/auth/register
  Body: { name, email, password, role }
  - Validates fields
  - Checks email not already taken
  - Creates user with isVerified: false
  - Generates 6-digit OTP, saves to user, sends email via nodemailer
  - Returns: { message: "OTP sent to email" }

POST /api/auth/verify-otp
  Body: { email, otp }
  - Checks OTP matches and is not expired
  - Sets isVerified: true, clears OTP fields
  - Returns: full user object + JWT token

POST /api/auth/resend-otp
  Body: { email }
  - Generates a fresh OTP, resends the email
  - Returns: { message: "OTP resent" }

─── LOGIN ────────────────────────────────────────────────────────────────────

POST /api/auth/login
  Body: { email, password }
  - Finds user, verifies password with bcrypt
  - Blocks if isActive is false
  - Blocks if isVerified is false (returns needsVerification: true)
  - Returns: full user object + JWT token

POST /api/auth/admin/login
  Body: { email, password }
  - Same as login but also checks role === "admin"
  - Admin accounts skip the isVerified check

─── PROFILE (protected — needs Authorization: Bearer <token>) ───────────────

GET /api/auth/profile
  - Returns the current user's data (no password, no OTP)

PUT /api/auth/profile
  Body: any of { name, password, phone, city, company, description, website, category }
  - NOTE: email is NOT changed here — use the email-change routes below
  - Updates only the fields that are sent
  - Returns: updated user object + new JWT token

─── EMAIL CHANGE (protected) ────────────────────────────────────────────────

POST /api/auth/request-email-change
  Body: { newEmail }
  - Checks new email is not already taken
  - Generates OTP, saves as pendingEmail on the user
  - Sends OTP email to the NEW email address
  - Returns: { message: "OTP sent to newEmail" }

POST /api/auth/confirm-email-change
  Body: { otp }
  - Verifies OTP matches and is not expired
  - Swaps user.email with user.pendingEmail
  - Clears OTP fields
  - Returns: updated user object + new JWT token

─── HOW JWT WORKS ───────────────────────────────────────────────────────────

  On login/register, server returns a token.
  Client stores it in localStorage as "planova_token".
  Every protected API call sends:  Authorization: Bearer <token>
  Server middleware (authMiddleware.js) decodes it and puts user info on req.user.
  Token payload: { userId, role }

9. AUTHENTICATION SYSTEM
================================================================================

HOW IT WORKS

  1. User registers (form) → POST /api/auth/register
  2. Server sends OTP to email
  3. User enters OTP on the OTP screen → POST /api/auth/verify-otp
  4. Server verifies OTP → returns user object + token
  5. Client calls login(data) from AuthContext
  6. AuthContext stores token in localStorage as "planova_token"
             and stores user object as "planova_user"
  7. On every page load, AuthContext reads localStorage to restore session
  8. Protected API calls include: Authorization: Bearer <token> header
  9. On logout: localStorage is cleared, user is set to null

AUTH CONTEXT (client/src/context/AuthContext.jsx)
  Provides:
    user        — the logged-in user object (name, email, role, company, etc.)
    login(data) — called after successful login/register, saves to localStorage
    updateUser(fields) — call after profile save to update sidebar/navbar live
    logout()    — clears everything, user becomes null

useProfile HOOK (client/src/hooks/useProfile.js)
  Used by profile pages to fetch fresh data from the DB.
  Separate from useAuth — AuthContext holds what the user logged in with,
  useProfile always fetches the latest from the server.

  Returns: { profile, loading, error, refresh }
  Also exports: updateProfile(data), initials(name)

ROUTE PROTECTION (client-side)
  App.jsx wraps dashboard routes inside role checks.
  If user is not logged in, they get redirected to /login.
  Admin routes are only accessible to role === "admin".

10. OTP EMAIL VERIFICATION
================================================================================

HOW THE OTP IS GENERATED
  Math.floor(100000 + Math.random() * 900000)
  → always a 6-digit number, e.g. "438291"
  → stored hashed? No — stored as plain string in User.otp
  → expires 10 minutes after creation (User.otpExpiry)

REGISTRATION FLOW
  Step 1: User fills form → POST /register → OTP emailed → show OTP screen
  Step 2: User enters OTP → POST /verify-otp → account activated → redirect to dashboard
  Resend:  POST /resend-otp → new OTP generated and emailed

EMAIL CHANGE FLOW
  Step 1: User clicks "Change Email" in profile → enters new email
       → POST /request-email-change → OTP sent to NEW email
  Step 2: User enters OTP → POST /confirm-email-change → email swapped in DB
       → new token issued (email changed so old token would be stale)

OTP EMAIL TEMPLATE
  Sent via nodemailer using Gmail SMTP
  HTML email with Planova branding, large OTP digits, 10-minute expiry notice

TO SET UP REAL EMAILS
  1. Go to your Google Account → Security → 2-Step Verification
  2. At the bottom: App Passwords → Create one for "Mail"
  3. Copy the 16-character password
  4. In server/.env set:
       EMAIL_USER=youremail@gmail.com
       EMAIL_PASS=your16charapppassword

11. USER ROLES
================================================================================

    - Can register and log in

    - Can view profile, edit name/company/city/phone/email/password
